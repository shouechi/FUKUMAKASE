# Outfit App — インフラ・運用・セキュリティ設計 v1.1

## 採用構成
- 2026-10-13の利用者指定により本番の公開・設定・定期処理を1つのCloudflare Worker `fukumakase` へ統合する。画面/APIを別Workerに配置する従来方針を変更する。開発時の2サーバーは維持する。
- `apps/web`: Next.js App Router / TypeScript / Tailwind CSS / shadcn/uiと、画面/API/CronをまとめるWorker入口。Cloudflare Workers上でvinextを第一候補として実行。ただし2026年10月時点でベータなので、実運用前に互換性試験とOpenNextへの切替可能性を維持。
- `apps/api`: Hono API / Zod / Hono RPCと定期処理の共通実装。Web Workerが直接利用し、`/api`・`/api/*`・`/health` をHonoへ振り分ける。別の本番API WorkerやService Bindingは不要。単独Wrangler設定はローカル開発専用とする。WorkerはNode.jsフル互換ではないため依存パッケージに注意。
- Supabase Free：PostgreSQL、Auth。認証メールは**Resend等の外部SMTP**に接続。Supabase標準SMTPは一般ユーザー向けの本番運用に適さない。メール・パスワードハッシュ・Google OAuth情報をSupabase Authに集約し、独自DBには複製しない。
- **画像保存はCloudflare R2の非公開Standardバケットを推奨**。Supabase Storage Freeは1GBで、最大100着×一般公開と相性が悪い。R2には10GB-monthなどの無料枠がある。DB/認証はSupabaseのまま。
- 天気：WeatherAPI Starter（7日予報の有料プラン、$7/月目安）を第一候補。費用が厳しくなる場合は3日無料予報＋後半は季節暫定の代案に切替える（週間表示には暫定と明示）。
- AI：OpenAI API。個別・全体利用上限、ジョブの非同期化、画像の圧縮。
- 定期処理：画面/APIと同じWorkerにCloudflare Cron Triggersを**5〜10分間隔の1トリガー**で設定する。日本時間の設定時刻前にdueユーザーを抽出。日曜夜の翌週生成も同一スケジューラで扱う。大量時はジョブを分割・後続Cronに繰り越す。R2バインディングとAPIのサーバーSecretsも同じWorkerに集約する。
- CI/CD：GitHub Actions、DB migration。MVPではCloudflareの自動Preview Buildsを無効とし、mainブランチのみ本番へ自動デプロイする。検証環境は本番と分離し、必要時に手動運用する。dev/staging/prodの設定を分離し、secretsはCloudflare環境変数とSupabase secret管理に配置。

## 構成図
```text
ブラウザ（スマホ/PC）
  -> Cloudflare Worker: fukumakase
     |-> 画面: Next.js/vinext
     |-> /api・/api/*・/health: Hono API（同じWorker内）
        |-> Supabase Auth + PostgreSQL
        |-> R2（非公開服画像）
        |-> OpenAI API（画像分類・選定）
        |-> WeatherAPI（天気予報）
Cron Trigger -> fukumakase内の既存scheduler -> generation_jobs -> ユーザーごとに生成・調整
```

## 予算設計（概算。為替・税・超過料は変動）
- Workers Paid基本料金：$5/月〜。Next.js SSRにはFreeのCPU 10ms/リクエスト制限が厳しい可能性があるため有料枠を第一候補。
- WeatherAPI Starter：$7/月〜。合計基本料金は約$12/月（概算で1,800円前後、実際の為替等による）。
- Supabase Free、R2 Free枠、Resend Free枠を使用。OpenAIには**月額500〜700円相当の運用目安**を設け、初期の総費用3,000円目標に余裕を確保。ドメイン、税、FX、超過リクエストは別途計上する必要があるため、3,000円は目標であり保証値ではない。
- 一般公開しても無料サービスで無制限利用を保証しない。100着/人の上限に加え、R2総使用量、無料メール100通/日、Workersリクエスト/CPU、DB容量、AI予算を監視し、上限に近づけば画像追加や一部AI処理を適切な案内付きで一時制限。API入口でもレート制限する。

## 画像セキュリティ
- MIME/拡張子/実体チェック、入力最大5MB（暫定）、WebP等の圧縮後目標100〜250KB、構図保持・メタデータ（EXIF位置情報）除去。
- R2バケット非公開。ユーザーが所有するキーだけに短期署名付きPUT/GETを発行。パスを`private/{userId}/{uuid}.webp`とし公開キャッシュを使わない。
- ファイル削除は削除ジョブと再試行、孤児ファイル清掃を設ける。URLに永続アクセストークンを埋め込まない。
- 服の削除後30秒間はUndo用に画像を非公開のまま保持する。期限後、ジョブがDBで所有権・削除世代・リースを検証して画像削除開始を確定し、その後R2削除と不在確認を実行する。R2とDBに分散トランザクションがないため、削除開始確定後はR2の成否にかかわらず復元を拒否し、失敗した削除は再試行する。
- 孤児清掃は有効な服・画像削除開始未確定の削除服・有効なアップロード予約を保護する。Undo期限切れだけを根拠に服画像を削除しない。退会中はUndoを許可せず、既存の退会削除手順を優先する。

## 障害/運用
- ジョブ：idempotency/lease、指数バックオフ、再実行可。誤って同じ朝に複数回計画生成しない。
- Undo導入時は新規マイグレーションを適用し、旧版の削除API・Cron・実行中Workerが停止したことを確認してから、新版で削除受付を開始する。旧版の`image_delete`と孤児清掃は猶予や削除世代を知らず画像を削除するため、混在稼働を許さない。導入前の削除行・旧形式の画像削除ジョブにUndo期限を後付けせず、新版の所有権・DB削除開始確認を経由して回収する。旧版に戻す場合も削除受付・Cronを停止して世代付きジョブを安全に処理するまで、旧版の画像削除経路を再開しない。
- 既存の2Worker構成からは、旧 `fukumakase-api` のCron停止・反映待ち後に統合Workerを公開する。mainの自動公開があるため、切替準備はマージより前に行う。コード変更だけで旧Workerや旧Cronが消えるとは扱わない。Secretsは統合Worker側へ設定し、旧Workerの削除は動作確認後の別作業とする（`operations.md`）。
- 外部天気障害：キャッシュ→季節暫定。AI障害：ルールベース。認証メール無料枠上限：Googleログインの代替を案内（メール登録は後で再試行）。画像容量上限：新規アップロードを制限し既存データは保護。
- ログは処理ID・失敗コード・モデル使用量の集計を基本とし、必要な場合のみ短期の仮名識別子を使う。メール、パスワード、認証トークン、OAuthトークン、署名付きR2 URL、画像、位置情報をログへ出力しない。Sentry等は送信情報と保存期間を精査。
- 退会：本人確認→以後のAPIアクセスを遮断→削除ジョブ→R2とDB削除→Supabase Authユーザー削除→完了表示。失敗時は再試行。既発行JWTが有効な間も削除済みユーザーのアクセスを拒否。バックアップ残存期間は別途公表。
- 必須公開文書：利用規約、プライバシーポリシー、AI/画像を外部サービスで処理する旨、問い合わせ先、退会方法。

## 追加：認証情報最小化のセキュリティ基準
1. `auth.users`を唯一のアカウント情報の正本とする。独自DBに`email`、`password_hash`、`display_name`、`phone_number`等を追加しない。必要な本人識別は`user_id UUID`のみ。
2. Google OAuthはログインに必要な最小スコープで構成し、Googleアクセストークンやプロフィールを独自DBに保存しない。
3. RLSを全ユーザー所有テーブルで有効化する。`service_role`は秘密情報としてサーバー内だけで利用し、利用範囲を可能な限り狭める。
4. R2バケットは公開設定を無効化し、GET/PUTを対象オブジェクト・短時間に制限する。署名付きURLは所持者が期限内アクセス可能なため、アクセスログに残さない。
5. パスワードはSupabase Authがハッシュ化して保存する。運営者は最小長8、必須文字種を英小文字・英大文字・数字・記号の全4種（Hostedの最強プリセット）に設定する。詳細は08、具体的な設定・検証手順は `operations.md` を正本とする。クライアント検証だけで強制済みと判断しない。管理画面の保護・登録のレート制限・ボット対策も運営側で設定する。
6. セッションCookie・OAuthコールバック・CSRF・Open Redirectを点検する。ログイン前後の権限を混同しない。削除中・退会済みアカウントは有効期限内のJWTを持っていてもアプリで拒否する。
7. Privacy by default：初回に氏名/住所/電話番号/生年月日等を要求しない。外部サービスへの送信と退会方法、バックアップの保持期間を公開する。
8. 障害解析・計測のためのデータは集計を優先。定期的にデータ保持を見直す。アプリ独自DBに生の認証関連データをコピーしない。

## セキュリティ責任範囲
| Supabase Authに委任 | アプリ側で責任を持つ |
|---|---|
| パスワードハッシュの保存・認証基盤 | 認証設定、Google OAuth設定、ログイン導線、メール配信 |
| セッション・ユーザーIDの発行 | Hono JWT検証、RLS、ユーザー権限の一貫性 |
| 認証データのスキーマ | クローゼット画像の非公開制御、R2署名URL、退会データ削除 |
| 認証サービス基盤の運用 | レート制限、秘密鍵管理、セキュリティ監視、プライバシーポリシー |
