# Outfit App — DB設計 v1.1
DB：Supabase PostgreSQL。Authは`auth.users`を利用。ユーザー所有テーブルの原則：`id uuid PK`、`user_id uuid FK auth.users(id)`、`created_at timestamptz`、`updated_at timestamptz`。実カラム・型はマイグレーションで固定。

## インデックスと不変条件
- `clothes(user_id, state, category) WHERE deleted_at IS NULL`、`daily_plans(user_id,target_date)`、`wear_logs(user_id,target_date DESC)`、`generation_jobs(status,lease_until)`。
- `clothes`の最大100着はクライアント側ではなくDBトランザクション/APIで判定。並行アップロード時にロック・一意なリクエストキーで超過を防ぐ。
- 削除済みの服はUndo猶予中も登録枠に含めない。復元時は有効な服と未使用かつ有効なアップロード予約の合計が100未満であることを、profileロック下で確認してから1着を戻す。他の登録・予約で上限に達していれば復元を拒否し、期限内の再試行は許可する。
- 服の削除・復元は本人の有効なprofile行と服行をロックする専用RPCで確定する。削除はDB時刻から30秒後を`undo_until`に設定し、削除世代を`deletion_token`で識別する。期限内かつ画像削除開始前の同一世代のみ復元できる。期限の境界は`clock_timestamp() < undo_until`とし、期限ちょうどの復元は拒否する。
- SQLのCHECKで、削除世代と期限が同時に設定されること、期限が削除時刻より後であること、画像削除開始には削除済み状態が必要なことを検証する。導入前の削除行は世代・期限なしのまま維持し、Undo対象にしない。復元時は削除状態と期限・世代を解除し、元の服属性と着用・洗濯状態を維持する。
- 削除・復元と、それに伴う再評価・分類ジョブの登録は同一トランザクションで行う。削除時に既存の分類リースを無効化し、`pending`の服を復元すると新しい世代の分類ジョブを作る。削除前の遅い分類結果は有効なリースがないため反映できない。
- 専用RPCの処理結果も`operation_receipts`に保存し、HTTP応答記録との間でプロセスが停止しても同じキーの再送が後の削除世代へ影響しないようにする。復元受付には入力した削除世代も保存し、同じキーで異なる世代を指定した場合は冪等性の衝突として拒否する。異なるキーで削除を繰り返しても、削除済みの現世代の期限は延長しない。
- R2削除ジョブは、DBで世代・所有者・有効なジョブリース・Undo期限切れを検証し、`image_purge_started_at`を確定してから画像を削除する。この確定と復元を同じロックで排他にし、実際のR2削除が失敗しても復元は許可しない。孤児清掃は画像削除開始未確定の服も参照中として保護する。
- 服の画像は専用R2非公開バケットに保管。DBは`image_key`のみ持ち、ユーザー認証後の署名付き短期URL/配信APIで表示。
- `wear_logs`は確定時だけ挿入。確定処理で`wear_log_items`と服の着用回数を同一トランザクションで増加。取り消し・修正は差分補正イベントを残す。
- 洗濯限界到達時は`state=laundry`。週計画内の「予定」は実着用と見なさず、将来日の利用可能性は予測値として扱う。
- 年齢・性別・氏名・電話番号・住所・生年月日などの個人属性は収集しない。メール・パスワード・GoogleトークンをアプリDBへ複製しない。

## セキュリティ/RLS
- 全ユーザー所有テーブルで`auth.uid() = user_id`を基本ポリシーとする。ユーザーIDをリクエストから信頼せず検証済みJWTから導出。
- `weather_cache`は認証済み読み取り、書き込みはバックエンドのみ。`ai_usage` `service_budget` `generation_jobs`は原則サーバー権限のみ。
- R2のキーは`private/{user_id}/{uuid}.webp`。バケットは公開しない。ダウンロード要求で所有権確認、期限の短いURLを払い出す。
- 退会は削除中フラグ/ジョブで以後のアクセスを遮断→対象R2画像を削除して検証→サービスDBの個人行を削除→Supabase Authのアカウントを削除する。FKには`ON DELETE CASCADE`を設定するがR2削除は別処理。Auth削除後でも短時間JWTが有効な場合があるため、削除中またはアカウント不在をAPI側でも拒否する。失敗時に安全に再実行可能とする。
- DBバックアップ内のデータ残存期間・削除を利用規約と運用手順に明示。一般公開前にエクスポート/復旧手順を確認。


## アカウント最小化のSQL骨子（追加）
```sql
create table public.profiles (
  user_id uuid primary key references auth.users(id) on delete cascade,
  onboarding_completed_at timestamptz,
  created_at timestamptz not null default now()
);

alter table public.profiles enable row level security;

create policy "only own profile"
on public.profiles for select to authenticated
using ((select auth.uid()) = user_id);
```
`INSERT/UPDATE/DELETE`の許可も最小権限に応じて別途定義し、すべてのユーザー所有テーブルにRLSを適用する。RLSをバイパスするサービス資格情報は定期ジョブなど必要最小限に限定し、その経路でも所有者チェックを行う。

## 個人データの分類
- 認証基盤のみ：メール、パスワードハッシュ、OAuth関連情報、認証ログ・セッション。独自DBにはコピーしない。
- アプリ独自DB：UUID、利用地域の最小単位、服のメタデータ、勤務曜日、提案・着用履歴、AI使用量。UUIDでも他データと組み合わせれば個人に関係する情報なので保護対象。
- ストレージ：プライベートな服の写真。位置情報などのEXIFはアップロード前に取り除く。
- 外部AIへ送るもの：分類時の必要な写真、提案時の最小限の服属性。メール・氏名・電話番号・セッション情報は送らない。
- 運用ログ：`request_id`、処理分類、失敗コード、概算課金量を基本にし、メール・JWT・画像・外部OAuthトークンを記録しない。
