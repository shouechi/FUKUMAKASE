## 再現と期待値

### R1: 予定を開くだけで既存の入力が失われる

API `GET /api/me/day-overrides/:date` が `{override:{is_workday:true,occasion:'external_visit',mood:'きれいめ'}}` を返す条件で日の編集を開く。旧UIは `o.occasion` を読んで `normal` に戻し、そのまま「予定だけ保存」で上書きした。正本の応答型を共有し、`o.override` の各値を表示・保存することが必要。

### R2: 洗濯と利用可否の混同

服詳細で「提案に使える状態」をオフにし、その服を洗濯済みにする。旧UIはオフ操作を洗濯待ちとして保存していたため、洗濯後に再び提案対象となった。`is_available=false` と `state=laundry` は別の状態であり、洗濯で前者を変えてはいけない。

### R3・R5: 退会の途中失敗

旧退会UIは受付応答の `job_id` を保存せず、その場でサインアウトした。認証ガードが未認証としてログインへ移動するため、受付・完了・失敗の表示が成立しなかった。旧ワーカーは `finish_job(success=true)` と個人データ除去のUPDATEを別々に実行し、後者の失敗後も再試行対象にならなかった。新実装は匿名の受付ページと、リース条件付きの原子的完了・匿名化を分離する。

### R4: 一回限りの認証コード

React StrictModeでcallbackのEffectが開始→cleanup→開始と実行されると、旧コードでは交換リクエストが2回発生し、最初の成功処理は `live=false` で捨てられる。2回目に「使用済みコード」が返ると成功済みなのに失敗画面となる。コードごとに交換promiseを共有し、リマウント側でも同じ結果を待つ必要がある。

### R6・R7: 外部天気と固定日の整合

`tests/review/adversarial.test.ts` で実行した回帰試験:

- 3日予報を取得した1秒後に、同じ7日表示を要求。修正前は外部呼出し2回、修正後は1回。
- 手動固定snapshotは25°C、取得済みの最新予報は5°C。修正前は低温警告と25°C表示が同居。修正後は同じoutfit IDを維持し、5°Cと低温警告を返す。

2026-10-11の確認コマンド: `pnpm exec vitest run tests/review/adversarial.test.ts`。天気関連2件の失敗を確認して担当へ報告後、同じ期待値の2件が成功。R10を追加後は3件成功。外部サービスを実際に呼ぶ試験ではなく、注入したDB/天気応答で制御フローと返却値を検証した。

### R8: 成功したが応答を受け取れないアップロード

画像PUTとDB作成を成功させ、最後の `POST /api/clothes` の応答だけ切断する。画面に残ったファイルで登録を再試行する。旧 `NewClothing.upload` は予約・PUT・作成をすべて新しいキーで実施し、DB側の冪等性では同一操作と判定できない。キーと予約を成功まで維持し、ファイルを変更した時点でのみ新しい操作にする必要がある。

### R9: 朝の処理期限と待ち行列

07:00指定の利用者が11人、待ち行列が空、10分間隔Cronという条件でも、旧実装は06:50に5人、07:00に5人しか処理せず、残り1人は07:10以降となる。分類・再評価ジョブが先に並ぶとさらに遅れる。DBの取得順を退会→日次→週次→分類→画像削除→再評価とし、1回のCron内で複数バッチを処理する。運用者は待ち行列の遅延・最古due時刻を監視し、利用者数と外部API遅延に応じて先行投入時間と同時実行数を調整する。有限の無料枠で任意の利用者数に期限保証はできない。

### R10: 初回設定完了時の空UPDATE

UIは「まず試す」で `{onboarding_completed:true}` のみ送る。旧APIはこの項目を除いた空オブジェクトを `user_preferences.update({}).select().single()` へ渡していた。PostgRESTの空PATCHは既存行を返さず、更新0行として応答するため、単一行要求に失敗する。この外部挙動は[PostgREST自身の回帰テスト](https://github.com/PostgREST/postgrest/blob/main/test/spec/Feature/Query/UpdateSpec.hs#L340)で確認した。新APIは変更項目がなければSELECTを使う。レビュー回帰試験は空UPDATEに単一行エラーを返すDBアダプタを使い、初期設定完了だけの要求が成功し、空UPDATEを発行しないことを確認した。

### R11: アカウント削除とジョブ追加の競合

服の登録要求がDB作成を完了した直後で一時停止し、別の退会処理が画像・DB・Auth・ジョブを削除した後、元の要求を再開して分類や再評価ジョブを挿入する。削除ジョブの再試行を可能にするため `generation_jobs` にAuth外部キーはなく、旧実装では削除済みUUID付きの通常ジョブが新規作成され、後に失敗状態で残った。APIの入口だけのアカウント確認では防げない。追加したSQLトリガーは通常ジョブの挿入時・本文更新時にactiveなprofile行をロックし、退会のtombstone設定と直列化する。退会開始のキャンセル更新や最終完了・匿名化は許し、通常ジョブの所有者変更は拒否する。

### R12: 外部ストレージ書込みの途中停止

認証済みアップロードがR2 PUTを開始→退会ジョブがprefix走査・空確認・DB/Auth削除を完了→先行PUTが完了→アップロードワーカーがアカウント再確認の直前に停止、という順序では、PUT後の補償削除が動かず画像が残りうる。予約行も消えているため予約ベースの孤児掃除では発見できない。これは実R2で故障注入済みという主張ではなく、await境界から特定した未検証の状態遷移である。進行中アップロードの永続的な記録・完了バリアや、受付有効期間を考慮した最終再走査が必要であり、単に最終走査の直後にAuthを削除したことだけでは耐障害性を証明できない。

さらに `tests/review/adversarial.test.ts` で、R2 PUT成功後のprofile照会をDBエラーにすると、補償削除の前で例外となり、応答503でもオブジェクトが残ることを実行確認した。これは実R2の停止試験ではなく、実際のHonoルートへ独立したDB/R2応答を注入した再現である。

修正後は上記DBエラーでも補償削除する。さらに、grantも利用者行も消えた後の遅延PUTを見つけるため、Cronが `private/` を100件ずつ走査し、service-onlyの `maintenance_state` にcursorを永続化する。消えた利用者・退会中の利用者の画像、および1時間以上経過し服・有効予約に参照されない画像を除去する。DB照会に失敗した場合は削除もcursor前進もしない。独立した2件のfixture試験が成功した。receiptの完了と外部PUTを単一トランザクションで排他するものではなく、停止した処理の残骸が後続のCron周期で除去される設計である。

### R13: 日本語の好みと分類メタデータの不一致

画面は「シンプル、きれいめ、カジュアル」を例示し、画像分類プロンプトは英語subtypeを要求する。旧ルールの `subtype.includes(styleKeyword)` では一般的な好みが一致しない。服の他の条件を同一にし、ID順で先にshirt、後にt_shirtを登録し、「カジュアル」を指定するとshirtが選ばれる。日本語/英語のスタイルを服属性へ対応付ける共通関数をドメイン層の正本とし、好みと気分の両方で利用する必要がある。

### R14: 手動固定日の予定洗濯警告

月曜の自動提案に洗濯上限1回のトップスを使い、火曜を同じトップスで手動固定する。週間ドメイン計算は予定着用数から火曜の洗濯警告を作るが、APIの最終応答で `planWarnings` を予定着用数なしで再実行し、その警告を失っていた。固定する服は維持しつつ、前日までの実際の生成結果（AI選択を含む）から予定着用数を引き継いで警告を計算する必要がある。独立回帰試験はコーデIDが変わらず、「洗濯」の警告が含まれることを要求する。

### R15: 解消した条件の古い警告が残る

手動固定コーデが低温時に「アウターの追加をおすすめ」と警告された後、最低22°C・最高28°Cへ予報を更新する。`planWarnings` は既存警告を全コピーしてから新しい警告を加えるため、低温条件がなくなっても警告を除去しない。服の利用可否や予測洗濯の改善でも同じ問題が生じる。可変条件の警告は現在の状態から再計算し、固定の注記と区別する必要がある。

### R16: 本番APIのURLにHTMLが返る

2026-10-13に本番 `https://fukumakase.hajimete-1105.workers.dev` の `/api/outfits/today`・`/api/me/usage`・`/api/me/preferences` を認証なしで読み取り確認した。すべて200の `text/html`、リダイレクトなしで、APIの `X-Request-Id` もなく、本文は `<!DOCTYPE html>` だった。Web Workerは全パスを受ける画面を持つが、本番のAPI転送がなく、開発専用Viteプロキシは本番で動かない。JSONの成功応答としてそのまま解析していたため、英語の `Unexpected token '<'` が画面に表示された。

Web WorkerのService Bindingから同一オリジンのAPI通信をHono Workerへ転送する。転送できない場合はJSONの503を返し、画面HTMLへ落とさない。認証ヘッダー・Origin・クエリ・本文・冪等キーは元のRequestのまま渡し、画像を含むResponseもそのまま返す。JSON・画像の認証と通信失敗処理を共通化し、JSONの媒体型・解析結果・共有契約を検証する。異常な本文や例外の原文を表示しない。変更結果が不明なHTML・不正JSON・通信断では冪等キーを保持する。

本番形式ビルドをMiniflareでWeb・APIの2Workerとして起動し、同じ3つのAPIパスが401のJSON・`no-store`・`X-Request-Id` を返すこと、`/today` は画面HTMLを維持することを確認した。API公開用の想定 `workers.dev` URLは本番確認時404だったが、公開アクセス無効の可能性もあるためAPI自体が未配備と断定しない。クラウドへの配備・認証済み本番操作は今回のローカル検証の証拠に含めない。

### R17: 再生成成功後の取得失敗で再生成を重ねる

Today・Weekの再生成POSTが成功した後、利用回数GETだけがHTMLや通信断になると、旧画面は全体を更新失敗として案内していた。POSTは既に正常成功し冪等キーが破棄されているため、再生成をやり直すと別操作で枠を追加消費する。POST成功と後続の読み取りを分け、成功時に選択画面を閉じ、利用回数の再取得を共通処理する。読み取り失敗からはGETだけを再試行し、回復するまでは再生成を無効にする。独立E2Eは日次・週間でPOSTを1回だけ成功させ、後続GETのHTMLを経て正常回復してもPOSTが増えないことを要求する。

2026-10-13の修正後検証: `pnpm typecheck` 成功、`pnpm test` は180件成功・接続未設定のDB/外部結合33件スキップ、`pnpm test:e2e` はPC/スマートフォンのChromiumで72件成功、`pnpm build:worker` 成功。画面試験のAuth/APIはネットワークfixtureであり、実メール・OAuth・認証済み本番操作の証拠ではない。独立した敵対的レビューでR17の修正と共通化を確認し、追加の実質不備は見つからなかった。本番への公開は行っていない。
