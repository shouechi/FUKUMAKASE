# Outfit App — 認証・個人情報最小化の設計 v1.1

## 目的と合意事項
アカウント関連の個人情報を自社アプリ側にできるだけ持たず、セキュリティ上の攻撃対象と管理負担を減らす。服画像や着用履歴をブラウザ内だけに保存するという意味ではない。質問11で合意済みの**メール＋パスワード、Googleログインの両方**は維持する。

## 決定事項
| データ | 正本の保存先 | アプリ独自DBへコピーするか |
|---|---|---|
| メールアドレス | Supabase Auth | しない |
| パスワードハッシュ | Supabase Auth | しない |
| Google OAuthの認証情報 | Supabase Auth | しない |
| UUID | Supabase Authで発行 | 外部キーとして保持 |
| 氏名・電話番号・住所・生年月日・性別 | 取得しない | しない |
| 服の写真 | 非公開Cloudflare R2 | オブジェクトキーのみ保存 |
| 好み・着用履歴・週間計画 | Supabase PostgreSQL | UUIDで管理 |
| 地域 | Supabase PostgreSQL | 天気取得に必要な地域粒度のみ |

## パスワード要件（2026-10-12確定）

- 新規登録とパスワード再設定は**8文字以上かつ英小文字・英大文字・数字・記号を各1文字以上**。Supabase Hostedの最強文字種プリセットに合わせる。
- 英小文字は `a-z`、英大文字は `A-Z`、数字は `0-9`。必須記号として数える範囲はASCIIの `U+0021–U+002F`、`U+003A–U+0040`、`U+005B–U+0060`、`U+007B–U+007E` の32文字（下記）。空白・全角記号・絵文字は必須記号として数えない。これら追加文字を一律禁止するという意味ではない。

```text
!"#$%&'()*+,-./:;<=>?@[\]^_`{|}~
```

- クライアントの検証・最小長・案内文は `packages/schemas` の `newPasswordSchema` / `passwordPolicy` を共有する。パスワードをトリム・正規化・ログ出力しない。サーバー側の最終判定はSupabase Authで行い、設定変更は運営者が `operations.md` に従って実施する。
- 追加のUnicode文字は禁止しない。クライアントの最小長はUnicodeコードポイント数で判定する一方、Hosted Supabaseの実装ではUTF-8バイト長の判定となり得る。長さと必須文字種について層間の完全一致を保証する受け入れ境界はASCII入力とし、リモート設定反映後に検証する。Unicodeを含む境界値はクライアント規則とHostedの実動作を別々に記録し、一致を未検証のまま保証しない。
- 最大長はSupabase Authの技術上限に合わせて**UTF-8で72バイト以内**とする（ASCII英数字・記号なら72文字以内）。新規登録・再設定の共有スキーマで `TextEncoder` によりバイト数を検証し、超過時は短くするよう案内する。Unicode文字は複数バイトとなるため72文字を保証しない。この上限は最小長・必須文字種とは別の制約であり、Dashboardの強度プリセット設定で追加する項目ではない。[Supabase Authの最大長検証実装](https://github.com/supabase/auth/blob/master/internal/api/password.go)
- ログインでは強度検証を追加しない。既存パスワードが新要件未満でも認証を妨げず、次回の登録・再設定から新要件を適用する。
- 最小長と必須文字種の設定、既存ユーザーへの影響は [Supabase Password security](https://supabase.com/docs/guides/auth/password-security) に基づく。リポジトリの実装変更だけではリモートAuth設定は更新されない。

## シーケンス
1. ユーザーはSupabase Authのメール＋パスワード、またはGoogle OAuthでログインする。
2. Supabase Authから発行されたアクセストークンをHono APIが検証する。認証済みの`sub`を利用して所有者を判断する。
3. アプリDBには`profiles.user_id`などUUIDと、服装提案に必要な設定だけ保存する。メールやGoogleプロフィールを転記しない。
4. 服画像は非公開R2に保存。Honoが対象服の所有者をDBで確認したうえで短時間のオブジェクト限定URLを発行する。
5. OpenAIへの画像分類リクエストは必要な画像と服属性だけに限定。識別可能なアカウント情報は送らない。
6. 退会時はアクセスを停止し、R2画像→サービスDB→Supabase Authを安全に削除する。失敗時は再試行する。

## API・DBの防御
- Supabaseのユーザー所有テーブル全件でRLSを有効化し、`auth.uid() = user_id`の本人アクセスを基本とする。Honoでサービス権限を使う場合も所有権を検証する。
- 全APIで`user_id`入力を認可の根拠にしない。認証済みトークンから取得する。
- Supabase APIの匿名キーは公開可能なキーと秘密キーを区別し、サービス権限トークンはサーバーのSecretに限定。
- セッションCookieはSecure/HttpOnly/SameSiteなど適切に設定し、OAuthコールバック・CSRF・URLリダイレクト先を検証する。
- アカウント削除は認証基盤だけで完結しない。JWTが期限まで形式上有効な場合も、退会中のユーザーのAPIアクセスを拒否する。

## 画像の取り扱い
- WebPへの変換・画像圧縮は許可。ただし服の構図は変えない。Exif位置情報などのメタデータは除去。
- R2公開URLを有効化しない。短期署名URLは共有されると期限内アクセスされるため、ログやメールに出さない。
- 服の写真は、コーデ画像SNS共有（後続v0.2）をユーザーが明示的に選ばない限り公開しない。

## ログ・第三者送信
- ログに生パスワード・メール・Googleトークン・JWT・画像本文・署名付きURLを残さない。
- 計測は個人特定のない集計を優先。短期の仮名識別子を使う場合も保存期間を決める。
- 画像解析のためOpenAIに写真を送る事実、Supabase/Cloudflare等で情報を処理すること、退会方法、バックアップの残存期間をプライバシーポリシーに記載する。

## デメリットと受け入れるトレードオフ
- Supabase Auth側にメールなどの認証データは残る。自社DBにコピーしなくてもサービス運営側の責任は残る。
- 障害時や認証基盤の仕様変更の影響を受ける。
- RLSとR2アクセスは独自実装・独自テストが必要。Supabaseに任せるだけでは画像漏えいを防げない。
- 登録服の所有権確認、退会時の非同期削除、監視・予算制限などはMVPでも必要。

## 非機能受け入れ基準
1. 独自DBに不要なPIIの列が存在しない。
2. 本人以外がDB・API・R2経由で服写真/履歴を取得できない。
3. 認証トークン・メール・画像・署名URLがアプリログに残らない。
4. メール/Google双方からログインでき、権限が混線しない。
5. 退会したユーザーのデータを削除し、削除途中のアクセスを防止できる。
6. プライバシーポリシーに必要な第三者送信・保持情報を記載している。
