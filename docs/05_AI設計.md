# Outfit App — AI・推薦ロジック設計 v1.1

## 役割の分担
- **決定的ルール**：出勤日・祝日、職場NG、利用不可/洗濯中、登録服の存在、着用回数、ユーザー手動ロック、再生成回数、予算。これらはAIに決めさせない。
- **AI**：服写真からの種類/色/季節推定、許可された候補同士の着合わせ順位づけ、短い理由の生成。AIが推定した服情報はユーザーが修正できる。
- **フォールバック**：AI APIが利用不可・全体予算到達時は、種類・季節・色・出勤条件・直近の着用を使うプログラム内スコアで決定。アプリ自体は止めない。

## 服の分類
入力：圧縮した1着の服画像。出力のJSON例：
```json
{"category":"top","subtype":"shirt","color":"white","seasons":["spring","autumn"],"confidence":0.84,"review_required":false}
```
`category`は4種類のみ。厚さは写真で自動確定せず未設定とする。曖昧な時は`review_required=true`とし、利用者に編集を促す。出力はZodで検証、DBの許可値以外は拒否。

## 今日の服・週間計画のアルゴリズム
1. `work_weekdays + holidays_off + day_overrides`から計画対象日を決定。休日は基本対象外。
2. 手動ロック済み日と確定済み着用履歴を保護。
3. 服候補から削除済み、洗濯中、着用限度到達、職場ルール違反、明らかな季節不適合を除外。
4. 天気を取得。最新成功データを使い、障害時は保存済み予報（鮮度表示）、古ければ季節ベース。7日予報が取得できるプランでも先の日付は暫定。
5. トップス・ボトムスを必須とし、靴・アウターは登録状況と天気から追加。未登録アイテムは架空のIDで補わず警告を返す。
6. 1週間の組み合わせは、翌日以降の利用可能性（洗濯待ち予測）と重複回避を考慮して順次割り当て。服が少ない場合は重複を許可するが、確定している洗濯制約を破らない。
7. AIに渡す候補は`id,category,subtype,color,seasons,thickness`の短いJSON。`wear_history.recent_clothes_ids`は確定済み実績に登場した候補IDを重複なしで渡し、`preferences.style_keywords`は設定した好み、`preferences.learned_styles`は実績から集計した候補のsubtype別回数を渡す。`planned_usage.projected_wears`は対象週の今日以降かつ対象日より前の未確定計画による服ID別の予定着用回数、`planned_usage.previous_items`はその直前の計画の`clothes_id,slot`のみとし、いずれも選択可能な候補に限定する。予定は着用実績と明確に区別する。天気・当日の気分・特別予定も渡し、画像は日々再送しない。
   - AIへは最近の実績と直前の予定の繰り返しをできる範囲で避け、週内の予定着用回数と実績から学習した好みを考慮するよう指示する。服が少なければ重複を許容し、洗濯・職場ルールなどの制約は引き続きサーバーが検証する。
8. AIが上位1セットを返す。ID参照・職場ルール・服の状態をサーバーで再検証。無効なら再選定またはルールベースに切替。
9. `reason_short`は日本語1行、過度な断定を避ける。ユーザーが気分や特別予定を指定していれば当該日にのみ反映。

## モデルと予算
- 2026-10-15の利用者指定により、写真分類と今日・週間コーデ提案は画像入力・構造化出力に対応する `gpt-6-luna` に固定する。モデル・単価・呼び出し設定は `apps/api/src/ai-config.ts` を共通で参照し、環境変数によるモデル切替や高額モデルへの自動切替は行わない。
- Responses APIは `service_tier: "default"`（Standard）、`reasoning: {effort: "none"}`、`max_output_tokens: 700`、`store: false`、厳格なJSON Schema出力を使用する。Standard単価は入力100万トークンあたり$0.10、出力$0.50（2026-10-15に[公式モデル情報](https://developers.openai.com/api/docs/models/gpt-6-luna)を確認）。料金改定時は共通設定を更新し、請求との整合を再確認する。写真はプロバイダが計上する入力トークンを使って概算費用を精算し、写真1枚あたりの定額とはみなさない。キャッシュ読込割引・書込料金・長文料金などの個別補正は行わないため、概算が実際の請求を上回る保証はない。
- 有料AIの開始には `OPENAI_API_KEY`、正の `AI_REQUEST_RESERVE_USD`、日本時間当月の有効なDB予算行を明示的に設定する。予約額の既定値は設けない。キー・予約額の未設定や不正値、DB予算の未設定・無効時には有料APIを呼び出さず既存の代替処理へ進む。予約額は想定する写真・リクエストの費用を実測して保守的に設定する。
- 固定モデルの出力精度・コストは本番前に20〜50サンプルで実測する。実APIによる品質・費用確認をモックテストで代替しない。
- 手動の日次再生成：ユーザーごと日本時間1日3回まで。週間全体再生成：日本時間の週に2回まで。自動日次と自動週間は個別枠だがサービス総予算には算入。
- `ai_usage`に呼び出し種別・トークン・概算ドル費用・成否を記録。実利用請求と突き合わせる。全体予算に近づけばAI無効化フラグを立てる（見積額で自動制御、費用の厳密な即時上限を保証しない）。
- 写真分類と週間計画には利用者あたりの短時間レート制限、サーバー全体の同時実行数上限を設ける。

## 非AI代替スコア（初期案）
- 基本合格条件：着用可＋NGではない＋カテゴリー充足＋季節に大きく外れない。
- スコア：スタイル一致+3、気温の適合+3、最近未着用+2、週内重複回避+2、色の相性+1、翌日重複-3。
- スコア順に決定的タイブレーク（服ID）で選択。スコアは検証時に変更可能。ユーザーの手動固定日は警告のみ。

## テスト基準
- AIが存在しない服のIDを返す→拒否。職場NG・洗濯中を含む→拒否。
- 2着だけ登録、靴/アウターなし、連日の雨、週途中で洗濯待ち、同日二重着用確定、ユーザー固定日、AI失敗、天気失敗、月予算到達を自動テスト。
- 企画KPI：提案をそのまま採用した割合、服選びの時間、週間の再生成率、初回登録完了率、2週目の継続率を計測。


## 個人情報最小化のためのAI入力方針（追加）
- 服の分類時にAIへ送るのは必要な圧縮画像のみ。ブラウザ側でEXIF位置情報などの画像メタデータを除去してから送信する。
- 日次・週間提案では写真を再送せず、アイテムID・分類・色・季節・着用状態・設定地域の天気など必要な属性のみに限定する。
- AIのリクエストへメールアドレス、氏名、Googleプロフィール、JWT、IPアドレスを意図的に含めない。AIプロバイダ側の保持ポリシーはプライバシーポリシーに明示する。
- AIの入出力全文や画像を運用ログに残さない。安全性や品質検証に必要なデータは本人への告知と保存期間を設け、匿名化または集計を優先する。
